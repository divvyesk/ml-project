# Used Car Price Prediction Using Machine Learning

Foundation of Machine Learning (SEML3211) — semester project, Weeks 1 to 15.

Predicts the selling price of a used vehicle from its specifications, using
the CarDekho dataset. This repository is the corrected and completed
codebase: it merges the Week 6 and Week 7–13 code, fixes the defects found in
both, and adds Weeks 14 and 15.

---

## 1. Quick start

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python scripts/run_all.py        # Weeks 5-15, end to end
streamlit run app.py             # Week 13 prototype
pytest -q                        # 35 tests
```

`run_all.py` regenerates every CSV, plot, model and report in this repository
from `data/car_data_raw.csv`. Nothing in `reports/` is written by hand.

## 2. Dataset

| Stage | Records |
| --- | --- |
| Raw (`data/car_data_raw.csv`) | 4,340 |
| Exact duplicates removed | 763 |
| Cleaned (`data/car_data_cleaned.csv`) | 3,577 |

Eight columns: `name`, `year`, `selling_price`, `km_driven`, `fuel`,
`seller_type`, `transmission`, `owner`. Target: `selling_price`, continuous,
in rupees.

### A note on `Present_Price`

Week 4 of the project document describes a **nine**-column CarDekho file that
includes `Present_Price`, and Weeks 5 and 6 describe the **eight**-column file
that was actually supplied. These are two different files published under the
same Kaggle dataset. This codebase uses the eight-column file — the one that
exists — and never fabricates `Present_Price`. Section 6 below explains what
that costs in accuracy.

## 5. Method

**Order of operations.** Split, then engineer, then fit. The train/test split
happens on the cleaned rows before any feature exists. `name_frequency` is
counted on training rows only. Imputation, scaling and one-hot encoding live
inside the sklearn `Pipeline`, so they are fitted per cross-validation fold.

**Target transform.** Selling price spans ₹20,000 to ₹89,00,000 and is
strongly right-skewed. Every estimator is wrapped in a
`TransformedTargetRegressor` that fits on `log1p(price)` and inverts with
`expm1`. Predictions and all reported metrics stay on the rupee scale.
`reports/target_transform_effect.csv` quantifies what this buys.

**Model selection.** Models are ranked by mean R² across 5-fold
cross-validation *inside the training split*. The test set is scored once,
after the winner is chosen. Ranking by the test score — which the earlier
Week 12 code did — makes the test set part of the fitting procedure and
inflates the reported number.

**Serving.** The fitted `reference_year` and `frequency_map` are stored in the
model bundle alongside the pipeline, and `src/predict.py` reuses them. Both
the app and the scripts call that one function.

Algorithms compared: Linear Regression, Ridge, Decision Tree, Random Forest,
XGBoost, plus a stacked ensemble of the tuned models.

## 6. On the "R² above 90%" objective

The project document sets R² > 0.90 as an objective. This codebase measures
and reports the real number; it does not tune against the test set until the
figure looks right, and it does not hard-code an accuracy anywhere.

The measured score falls short on the rupee scale, and the reason is the
dataset rather than the modelling. The 90–95% results quoted in the Week 3
literature review come from the nine-column CarDekho file, where
`Present_Price` — the current showroom price of the same model — carries most
of the signal. On the eight-column file the same algorithms cannot reach that
number.

Two diagnostics in `reports/final_report.md` locate the shortfall: R² measured
on the log scale, and R² with the most expensive 1% of test vehicles removed.
Both sit far above the headline figure, which means the model handles the bulk
of the market well and loses its score on a thin luxury tail. The honest
statement of the result, with what would be needed to close the gap, is in
section 14.6 of the generated report.

## 7. Tests

```bash
pytest -q
```

Tests that need a trained model or a cleaned CSV skip themselves when those
artifacts are absent, so `pytest` is safe to run on a fresh clone. They cover
the cleaning-stage counts against the documented 4,340 / 763 / 3,577 figures,
the leak-free frequency map, the log-transform round trip, and the
train/serve consistency of the prototype.
